# 주변 공중화장실 찾기 웹페이지 — 설계

작성일: 2026-11-03

## 1. 무엇을, 왜

**상황:** 밖에서 갑자기 배가 너무 아픈데 주변 화장실을 찾을 수 없을 때.

**만들 것:** 휴대폰으로 URL을 열면 곧바로 "지금 열려 있는 가장 가까운 공중화장실"과 그곳까지 가는 방법을 보여 주는 웹페이지. 데이터는 행정안전부 공공데이터(API)를 기반으로 한다. 개인용이지만 URL만 알면 다른 사람도 접속할 수 있어야 한다.

급한 상황에서 쓰는 도구이므로 **속도와 단순함**이 가장 중요하다. 열자마자 답이 보여야 하고, 고르거나 입력할 것이 없어야 한다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
- 페이지를 열고 위치 권한을 허용하면 몇 초 안에 가장 가까운 화장실이 보인다.
- 그 화장실이 지금 열려 있는지, 어디에 있는지 한눈에 알 수 있다.
- 버튼 한 번으로 카카오맵 / 네이버지도 / 구글맵 길안내로 넘어간다.
- 누구나 `https://` URL로 접속할 수 있다. 로그인이나 앱 설치는 필요 없다.
- 데이터가 사람의 손을 거치지 않고 API로 자동 갱신된다.

**비목표 (이번 범위 아님)**
- 리뷰, 평점, 사용자 제보 및 수정
- 실내 지도, 층별 안내
- 로그인, 즐겨찾기, 계정
- 앱 자체에서 경로 계산 (길안내는 외부 지도 앱에 맡긴다)
- 해외 지역

**실패 조건 (동작은 해도 실패로 보는 것)**
- 첫 화면이 뜨기까지 오래 걸린다 (특히 모바일 데이터 환경에서).
- 닫힌 화장실을 "열림"으로 안내한다.
- 가장 가까운 곳을 보기 전에 무언가를 눌러야 하거나 입력해야 한다.
- API 키가 페이지 소스에 노출된다.

## 3. 사용자가 정한 것

- **화면 구성: B안.** 화면 전체가 지도이고, 아래에서 카드가 올라온다.
  - 지도: 내 위치(파란 점)와 주변 화장실 핀이 표시된다. 핀은 색과 기호로 상태를 나타낸다(✓ 열림 초록, ? 확인 필요 노랑, ✕ 닫힘 회색, 사용자 요청 2026-11-07). 추천 장소에는 "추천" 글자를 붙이되 색은 그 상태를 따른다. 지금 카드에 보이는 핀은 크게, 진한 테두리와 빛 번짐으로 표시한다(사용자 요청 2026-11-07). 지도 위에 범례를 둔다.
  - 아래 카드: 열림 상태 뱃지, 화장실 이름, 거리와 도보 시간, 주소, 길찾기 버튼 3개(카카오맵 / 네이버 / 구글).
  - 다른 핀을 누르면 카드가 그 화장실 정보로 바뀐다.
  - 카드 어디든 아래로 끌면 이름과 거리만 남기고 접혀서 지도를 크게 볼 수 있다. 끄는 동안 카드가 손가락을 따라오고 놓으면 부드럽게 제자리로 간다. 접힌 카드는 위로 끌어 올려야 펼쳐지고, 누르기만 해서는 열리지 않는다(사용자 결정, 2026-11-07). 지도에서 핀을 누르면 펼쳐진다. 카드 위의 조작으로 지도가 움직이지 않는다.
  - 시안: `.superpowers/brainstorm/831-1793715393/content/first-screen.html`의 B
- **카드에 꼭 보여야 할 정보:** 열려 있는지, 어디에 있는지.
- **길찾기 앱:** 카카오맵, 네이버지도, 구글맵. 세 가지 모두 제공한다.
- **데이터:** 행정안전부 「공중화장실정보 조회서비스」 API를 쓰고, 자동으로 갱신한다.
- **갱신 주기:** 일주일에 한 번 정도면 충분하다.
- **구성 방식 (제안을 사용자가 그대로 수락):**
  - 무료 정적 호스팅에 올려 `https://` URL로 공유한다.
  - 서버 없이 운영한다. 정기 자동 작업이 데이터를 만들고, 페이지는 그 결과 파일을 읽는다.
  - 지도는 API 키가 필요 없는 무료 오픈 지도를 쓴다.
  - 주소 → 좌표 변환 API를 사용한다. 사용자가 공공데이터포털 키와 도로명주소 API 키(검색, 좌표제공)를 직접 발급한다.

## 4. 데이터 — 확인된 사실

출처: <https://www.data.go.kr/data/15155058/openapi.do> (2026-11-03 확인)

- 엔드포인트: `https://apis.data.go.kr/1741000/public_restroom_info_v2`. REST 방식이며 JSON/XML로 응답한다.
- 인증: `serviceKey` (공공데이터포털에서 발급). 개발계정 트래픽은 일 10,000건.
- 페이징: `pageNo`, `numOfRows`(최대 100), `returnType=json`
- 필터: 갱신시각(`DAT_UPDT_PNT`), 도로명주소 LIKE(`LCTN_ROAD_NM_ADDR`), 지자체코드(`OPN_ATMY_GRP_CD`), 데이터기준일(`DAT_CRTR_YMD`)
- 제공 항목: 화장실명, 도로명주소, 남녀·장애인·어린이용 위생시설 수, 개방시간 등
- 갱신 주기: 매일 (조회일 기준 이틀 전 데이터)
- **2025년 2월부터 WGS84 위도·경도를 제공하지 않는다.** 위치로 검색할 수도 없다.
  → 주소를 좌표로 바꾸는 단계가 반드시 필요하다.
- 조회 오퍼레이션 경로는 `/info_v2`다. 응답은 `response.header.resultCode`("0"이면 정상), `response.body.totalCount`, `response.body.items.item[]`. 2026-11-03 기준 전국 53,578건이다.
- 주요 필드: `MNG_NO`(관리번호), `RSTRM_NM`(화장실명), `LCTN_ROAD_NM_ADDR`(도로명주소), `LCTN_LOTNO_ADDR`(지번주소), `OPN_HR`(개방시간 구분), `OPN_HR_DTL`(개방시간 상세), 남녀·장애인·어린이용 변기 수(`*_TOILT_CNT`, `*_URNL_CNT`).
- 1,000건 샘플을 보면 `OPN_HR`은 분류값이다. `상시` 62%, `정시` 약 35%(세부 시간은 `OPN_HR_DTL`에 있음), `미개방`이 일부 있다.

## 5. 전체 구조

```
[GitHub Actions, 주 1회 (사용자 결정) + 수동 실행 버튼]
  1) 행정안전부 API에서 전국 데이터 전부 받기 (100건씩 페이징)
  2) 주소 → 좌표 변환 (새 주소나 바뀐 주소만; 이전 결과는 캐시에서 재사용)
  3) 개방시간 텍스트를 해석해 구조화된 형태로 저장
  4) 페이지용 데이터 파일 생성 → 저장소에 커밋 → GitHub Pages 배포
        ↓
[GitHub Pages: 정적 페이지 + 데이터 파일]
        ↓
[사용자 휴대폰 브라우저]
  위치 가져오기 → 근처 데이터 읽기 → 거리 계산 → 지도와 카드 표시
```

- **호스팅: GitHub Pages** (제 결정). GitHub Actions와 한곳에서 관리할 수 있다. 사용자에게 GitHub 계정이 필요하다.
- **API 키:** GitHub Actions Secrets에만 저장한다. 페이지와 저장소 코드에는 넣지 않는다.
- **지도: 네이버 지도 Dynamic Map** (사용자 결정, 2026-11-05). 지도 표시 전용이다. Client ID는 페이지 소스에 공개되고 등록한 URL에서만 작동한다. Client Secret, Directions, Geocoding은 쓰지 않는다. 지도가 실패해도 카드는 보여야 한다.
- **좌표 변환 API: 행정안전부 도로명주소 API (business.juso.go.kr)** (사용자 결정, 2026-11-03). 한 주소마다 검색 API(`addrLinkApi.do`)로 주소 키를 얻고, 좌표제공 API(`addrCoordApi.do`)로 좌표를 받는다. 받은 좌표는 UTM-K(EPSG:5179)이므로 WGS84로 바꾼다. VWorld, 카카오, 네이버는 결과 저장을 금지해서 쓰지 않는다. 도로명주소 API는 공공데이터포털에서 "이용허락범위 제한 없음"으로 표시되어 있다. 일일 한도는 빌더가 확인한다. 처음에는 전국을 한 번에 변환해야 하므로 한도를 넘으면 며칠에 나눠 채우도록 한다.
- **저장소 공개 여부:** 공개 저장소로 한다 (제 결정). 무료 GitHub Pages의 조건이고, 담기는 데이터도 공공데이터다. 빌더는 도로명주소 API 약관에 결과 저장이나 재배포를 금지하는 조항이 없는지 키 발급 때 확인한다.
- **제공 지역: 서울·경기만** (사용자 결정, 2026-11-05). 다른 지역은 갈 일이 없어 당장 필요 없다. 코드는 지역 설정만 바꾸면 넓힐 수 있게 둔다.
- **좌표 변환 범위의 한계:** 도로명주소 API는 건물 기준이라 건물 없는 공원·산의 지번 주소는 좌표를 받지 못한다. 전국 표본 200개 중 83.5%가 성공했다(2026-11-05).
- **좌표 캐시:** `주소 → 좌표` 캐시를 저장소에 보관해 다음 실행부터 새 주소만 변환한다. 변환에 실패한 주소는 지도에 표시하지 않고 기록만 남긴다.

## 6. 화면 동작 세부

**처음 열 때**
1. 위치 권한을 요청한다.
2. 허용하면 내 위치를 중심으로 지도를 표시하고, 가장 가까운 곳의 카드를 바로 띄운다.
3. 거부하거나 실패하면 "위치 권한이 필요해요" 안내와 다시 시도 버튼을 보여 준다 (제 결정). 이 경우에도 지도는 볼 수 있게 한다.
4. 지도를 눌러 내 위치를 직접 정할 수 있다 (사용자 결정, 2026-11-06). 위치를 얻었을 때도 "내 위치 직접 찍기"로 쓸 수 있고, "현재 위치 사용"으로 되돌아온다.

**"가장 가까운 곳" 고르기 규칙** (제 결정)
- 후보는 내 위치에서 가까운 순서로 정렬한다.
- 확실히 "열림"인 곳 중 가장 가까운 곳을 기본 추천으로 강조한다.
- "운영시간 확인 필요"인 곳이 추천 장소보다 훨씬 가깝다면 숨기지 않는다. 핀은 노란색으로 그대로 보이고, 기준은 빌더가 정한다 (예: 추천 장소 거리의 절반 이하).
- "닫힘"인 곳은 회색 핀으로 표시하고 추천하지 않는다.
- **근처에 확실히 열린 곳이 없을 때** (사용자 결정): 가장 가까운 "운영시간 확인 필요" 화장실을 경고 문구와 함께 추천 카드에 띄운다. 예: "열려 있는지 확인되지 않았어요. 개방시간: {원문}". 이렇게 하면 데이터를 멀리까지 읽어 오지 않아도 된다. "근처"의 범위(예: 도보 10분 ≈ 700m)는 빌더가 정한다. 그 범위 안에 "확인 필요"인 곳도 없으면 범위를 넓혀 가장 가까운 열림 또는 확인 필요 장소를 찾는다.

**열림 상태 판정** (`지금 열림` / `운영시간 확인 필요` / `닫힘`)
- 개방시간 구분 `OPN_HR`에 따라 다음과 같이 판정한다 (사용자 결정, 2026-11-03).
  - `상시`는 24시간 개방이므로 "지금 열림"이다.
  - `정시`는 `OPN_HR_DTL`의 세부 시간을 해석한다. 세부 시간은 자유 텍스트다 (예: "09:00~18:00", "9시~18시", "05:00~25:00", "(평일)09:00~18:00", "근무시간 내").
  - `미개방`은 일반에 개방하지 않는 곳이므로 데이터에서 제외한다.
  - 그 밖의 값이나 빈칸은 "운영시간 확인 필요"다.
- 세부 시간은 확실히 해석되는 것만 열림이나 닫힘으로 판정하고, 나머지는 모두 "운영시간 확인 필요"로 둔다. **애매하면 열림으로 판정하지 않는다** (실패 조건: 닫힌 곳을 열림으로 안내).
- 해석은 데이터를 만드는 단계에서 미리 해 둔다. 실제 데이터를 보고 패턴 목록을 만드는 일은 빌더가 한다. 한국 시간(KST) 기준이다.

**카드**
- 상태 뱃지, 이름, 거리(m 또는 km), 도보 시간(직선거리 ÷ 분당 약 67m, "약"으로 표기), 도로명주소, 개방시간 원문
- 길찾기 버튼 3개. 목적지 좌표와 이름을 넘기고, 출발지는 현재 위치로 한다.
  - 카카오맵: `https://map.kakao.com/link/to/{이름},{위도},{경도}`
  - 네이버지도: 앱 스킴 `nmap://route/walk?dlat=..&dlng=..&dname=..&appname=..`. 앱이 없으면 웹으로 넘긴다.
  - 구글맵: `https://www.google.com/maps/dir/?api=1&destination={위도},{경도}&travelmode=walking`
  - 정확한 형식과 동작은 빌더가 실제 기기에서 확인한다.
- 장애인·어린이용 시설 수 같은 부가 정보는 작게 보여 준다 (제 결정).

**기타**
- 휴대폰 화면을 기준으로 만들고, PC에서도 깨지지 않게 한다.
- 한국어 전용이다.
- 화면 하단에 데이터 출처(행정안전부)와 마지막 갱신일을 작게 표시한다.

## 7. 성능

- 첫 화면이 빨라야 한다. 전국 데이터 전체를 한 번에 내려받게 하지 않는다.
- 데이터 파일을 지역 격자(타일) 단위로 나누고, 내 위치 주변 격자만 읽는 방식을 권장한다. 격자 크기와 형식은 빌더가 정한다.
- 화면 목표: 위치를 얻은 뒤 1~2초 안에 카드가 표시된다 (모바일 LTE 기준).

## 8. 빌더에게 맡기는 것

- 프런트엔드 기술 선택 (단, 가볍게: 정적 HTML/JS나 작은 번들)
- 데이터 처리 스크립트의 언어 선택
- 실제 API 응답 필드 확인과 매핑
- 개방시간 해석 패턴 목록
- 데이터 파일 형식과 격자 크기
- 지오코딩 API의 한도 확인, 재시도와 분할 실행 방식
- 핀 색과 세부 디자인 (시안 B를 따른다)
- 테스트 범위

## 9. 사용자가 해야 할 일 (빌드 중에 안내)
